## 冒烟测试机制：符号级调试的端到端回归

第 9.2 章从 9.2.22 一路写到 9.2.42，godbgv2 的命令数涨到 39 个；9.3 章的高级特性还会继续给命令加开关、加输出形态。每加一条命令，就多一组交互路径。这些路径的正确性，单元测试基本兜不住：`go test ./...` 能证明 DWARF 解析器解对了行号表，却证明不了 `break main.go:28` 经命令行、RPC、debugger 一路传到 proc/target 之后，停在的确实是源码第 28 行。

本节讲的就是这一层保障：符号级调试器的端到端冒烟测试（smoke test）。机制本身在 6.5 节已经实现并讲透——`--init` 回放、`scripts/smoke.sh` 驱动器、`=`/`!=` 断言——本节不重复 harness 的实现，只讨论“脚本从个位数涨到 36 个之后，怎么组织、怎么断言、怎么和提交纪律配合”。

> 命名上做一次统一：仓库叫 godbgv2，编译出的二进制叫 godbg；早期书稿里它叫 tinydbg，那些称呼按历史保留。

### 实现目标

本节不新增一行 harness 代码，目标有三个：

- 说明符号级调试为什么必须做端到端冒烟，单元测试补的是哪一段、补不了哪一段；
- 梳理自研 DSL 在符号级用例里的几个关键用法：`--init` 批量回放、`@capture`、`@set`、`@skip-if`，以及断言的作用域；
- 给出 36 个脚本的覆盖版图与缺口，并把“脚本随代码同提交”与 tag/提交纪律绑定。

[6.5 冒烟测试机制](../../6-develop-inst-debugger/5-smoke.md)已经把三件套讲完了，9.3.111 这一节只讲“上量之后”的组织方式。

### 基础知识

#### 1. 单测绿了，为什么还不敢改

godbg 的一次断点命中要穿过五层：命令行解析（`cmd/`）→ `api.Client` 接口 → rpc2 编解码 → debugger 门面 → proc/target 的 ptrace 操作。`pkg/dwarf`、`pkg/proc` 里的纯函数都有单测，但“命令有没有注册”“RPC 字段有没有漏传”“断点清除后有没有把 0xCC 还原”这类接线问题，只有把整条链路跑起来才会暴露。

符号级又比指令级多一层麻烦：输出里的行号、函数名、线程 id、goroutine 状态都来自目标进程和它的 DWARF 数据，没有一份稳定的“期望输出”可以放在单测里。fixture 换个工具链、换个 Go 版本，地址和行号就会漂移，写死期望值的测试很快就变成维护负担。

#### 2. 交互式命令的组合爆炸

断点、continue、bt、print、threads、goroutine 这些命令单独看都不难，难在组合：先 `break` 再 `continue` 才有停点，先 `threads` 再 `thread <id>` 才谈得上线程视角，`call` 之后还要再 `continue` 验证现场没被破坏。39 个命令按上下文组合，手工逐条验证不可重复，也很难交给 CI。冒烟测试的价值，就是把这些组合固化成可回放、可断言的会话。

#### 3. 断言只认“最近一条命令”

`=` 与 `!=` 不是在整个会话日志里做 grep。驱动器按回显标记 `godbg> ` 把输出切成逐命令片段，断言只看“最近一条 godbg 命令”的那一段。这个边界是刻意的：

- 正向断言不会因为前面某条命令碰巧打印过相似文本而误判通过；
- 反向断言才能表达“`clear` 之后 `breakpoints` 里不再有这条断点”——它检查的是 `clear` 自己那一段，而不是启动信息的残留。

断言用 POSIX 扩展正则（`grep -E`），模式里的方括号、括号、点号要按正则转义。符号级输出里的 `\[_Grunning\]`、`runtime\.main\(\)` 都是这个原因。

### 代码实现

机制不是本节新增的。为了让后面的组织约定有落点，这里先把它在符号级用例里的形态压缩成三件套、用例和三个会话值，再谈上量后的约定。

#### 1. 三件套

```text
testdata/script/ch9.2.40.txt   用例：一个书稿小节一个脚本文件
scripts/smoke.sh               驱动器：准备环境、启动会话、切分输出、核对断言
godbg --init <file>            回放器：在会话内逐行执行调试命令
```

指定 `--init` 后，会话进入批量模式：逐行读脚本、逐条执行，命令输出带 `godbg> ` 前缀回显，回放结束自动退出。批量模式不创建 liner，避免终端 `tcsetattr` 与 `timeout` 的进程组问题——这条坑 6.5 已经解释过，此处不重复。回放中某条命令报错会终止回放、把错误写到 stderr，后面的断言自然就对不上了；因此用例里每条关键命令后面都要跟断言——只依赖退出码，不足以证明会话内部每条命令都成功。

#### 2. 用例长什么样

以 `testdata/script/ch9.2.41.txt` 的线程切换段为例：

```text
@exec _fixtures/vars
break main.go:28
continue
=thread [0-9]+ status: stopped: trace/breakpoint trap
threads
=\* Thread [0-9]+ at 0x4b1b87 main\.main .*vars/main\.go:28
@capture TID '  Thread ([0-9]+) at .*'
thread $TID
=switched to thread $TID at .*
```

`@exec` 决定会话从哪个 fixture 启动；中间几行是真正的调试命令；`=` 逐条核对最近命令的输出；`@capture` 从 `threads` 的输出里取出第一个非当前线程的 tid，再把它代入 `thread $TID`，连断言里的 `$TID` 也一起替换。

#### 3. 三个“只在会话里存在”的值

- **`@capture`：会话中生成的值。** tid 由内核分配，只存在于本次会话的输出里；重跑一次就是新进程、新 tid，所以捕获必须由 godbg 在同一次会话内闭环完成。实现上分两层：回放器替换后续命令行，`smoke.sh` 在会话结束后替换断言模式。两层做同一件事，是交互式程序测试 harness 的结构性成本。
- **`@set`：启动前就能确定的值。** 例如非 PIE fixture 的 `main.counter` 地址，用 `go tool nm` 在会话前算出来，再替换进命令和断言。它和 `@capture` 的方向相反：一个在会话前准备环境，一个在会话内留下现场。
- **`@skip-if`：环境能力探测。** 例如 WSL2 内核对硬件监视点支持不全，探测命中就跳过整条用例并计为通过；CI 的真内核则完整执行。它只用于“这台机器没有这个能力”，不能用来掩盖真实失败。

#### 4. 上量后的组织约定

- **一节一脚本，文件名跟小节编号走。** `make smoke S=ch9.2.40` 直接映射到 `testdata/script/ch9.2.40.txt`；脚本内部再按“启动 → 主路径 → 收尾”分段，不按命令拆成多个文件，因为会话上下文跨不了进程。
- **一条主路径配几条硬断言。** 先保证这条命令能跑通、输出锚得住（地址、行号、函数名至少锚一个），再补边界情况；不要一上来就追求全部分支。
- **运行时值和地址不写死。** 该 `@capture` 的用 `@capture`，该 `@set` 的用 `@set`；写死 tid 或链接地址，等于把用例变成某台机器的快照。
- **断言放宽时序，不放宽语义。** goroutine 状态、线程停点会随调度波动，用 `_G(runnable|waiting)` 这类宽松模式；但“停在哪个函数、哪一行”不能含糊。
- **新脚本至少连跑 3–5 遍。** fixture 固定用 go1.24.13 构建，保证地址和行号可复现；换工具链要预期一批断言失效。

### 执行测试

跑单个小节：

```bash
$ make smoke S=ch9.2.40
smoke: running testdata/script/ch9.2.40.txt
smoke: all passed
```

`make smoke` 会先 `make build`、`make fixtures`，再驱动全部脚本；带 `S=` 时只跑指定的一节。日常改完代码，至少过一遍 `make build`、`make vet`、`make test`、`make smoke`；CI 的门禁只会更全。

#### 覆盖版图

`testdata/script/` 下共 36 个脚本：

| 范围 | 数量 | 主要内容 |
| --- | --- | --- |
| ch6 全章（6.5–6.17、6.18.1–6.18.5、6.19） | 19 | 启动、清理、反汇编、断点、步进、内存与寄存器、多线程 |
| ch9.2.22–26、32–42 | 16 | 断点、trace/watch、funcs/vars、bt、stepout/goroutines、多线程、thread、call |
| ch12.8 | 1 | 关闭 ASLR 后 Rip 稳定 |

缺口也明确记在 `docs/FEATURE-MATRIX.md` §11⑤：ch9.2.27–31、core（9.2.15）、connect/headless（9.2.16）没有脚本。三类缺口性质不同：

- 27–31 里的 continue、pmem、pregs 在别的脚本里被间接用到（断点、内存、寄存器用例），缺的是它们自己的独立断言组合；next 本身还是桩，暂时也没有可断言的输出；
- core 的 `cmd/core.go` 还是桩，接线之前写端到端用例只会验证一个“TODO”；
- connect/headless 需要第二个进程或第二个客户端，而当前 harness 只驱动一个会话，得先扩展 DSL，不是加一个 `.txt` 就能解决。

把这些缺口写进能力矩阵，比假装“36 个脚本全覆盖”诚实；补的时候也按风险排序，而不是按编号顺序。

#### 加一条新脚本的流程

1. checkout 对应小节 tag，`make build`、`make fixtures`；
2. 新建 `testdata/script/<section>.txt`，从最小主路径写起；
3. `make smoke S=<section>`，改到通过，再连跑 3–5 遍确认稳定；
4. 代码与脚本放进同一个提交，`make build`/`vet`/`test`/`smoke` 全绿后再提交。

#### 和 tag、提交纪律的关系

godbgv2 的铁律 5 规定：一个小节一个提交，subject 是纯描述、不写小节号；提交消息最后一段带 `Section` 与 `Section-Num` 两个 trailer；tag 由 `scripts/retag.sh` 根据 trailer 和书稿 SUMMARY 派生，禁止手工打。纯工具或文档维护提交不带 trailer，因而也不会派生 tag。

这条纪律和冒烟测试是绑在一起的：读者 checkout 任意 `chX.Y` tag，都应该得到可编译、可运行的代码。如果代码先提交、脚本下个提交再补，tag 指向的提交就缺一份能复现书里输出的用例；如果脚本红了还提交，tag 本身就不该存在。所以“每节提交必须编译 + 测试全绿”不是 CI 的礼貌提醒，而是 tag 可信度的前提。

> ps：本节本身没有代码改动。`ch9.3.111` 指向的提交只把本节编号记进了当时的 `docs/tags.map`；harness 的实现在 6.5 对应的提交里，后来 tag 改由 retag.sh 统一派生。这也是迁移前后的一处历史差异：现在纯文档提交不再带 trailer、不再打 tag。

### 本节小结

冒烟测试机制在 6.5 节已经完成：用例脚本表达输入与期望输出，`--init` 回放器在会话内执行命令，`smoke.sh` 在会话外核对断言。到了符号级阶段，真正变化的是规模和组合——36 个脚本覆盖 ch6 从 6.5 起的全部小节与 ch9.2 的大部分命令，断言、运行时值、环境探测各有各的写法，覆盖缺口也必须显式记录。

本节没有重新发明 harness，而是把“上量之后怎么组织”讲清楚：一节一脚本、断言只认最近一条命令、运行时值不写死、脚本与代码同提交。做到这些，书里的示例、godbgv2 的实现、读者 checkout tag 跑出来的结果，才可能长期保持一致；漏掉其中任何一条，冒烟测试就会退化成“作者机器上曾经通过一次”的记录。
