## 日志系统设计

### 多层次调试器与日志挑战

现代调试器是一个复杂的系统，通常包含多个层次和组件，如核心调试引擎、RPC 通信层、符号解析、栈回溯、变量求值等。在这种复杂的系统中，如果没有一个精心设计的日志系统，会遇到以下问题：

1. **问题定位困难**：当调试器出现问题时，难以快速定位问题发生在哪个层次或组件中；
2. **日志混乱**：不同层次的日志混杂在一起，缺乏清晰的分类和标识；
3. **信息不完整**：关键上下文信息缺失，难以理解日志产生的具体场景；
4. **性能影响**：不当的日志记录可能会影响调试器的性能。

godbgv2 的日志系统目标不是做成 dlv 那样的生产级日志框架，而是为教学提供一个**足够小、能讲清楚分层与开关**的实现：默认安静，需要时能打开，出问题能落到文件。

### godbgv2 的日志设计

godbgv2 没有引入 `slog`，也没有为每个组件维护独立的 logger；它只在 `pkg/log` 提供一个全局的分级日志器（`pkg/log/log.go`）。核心设计只有三点：

- **三个级别**：`LevelDebug`、`LevelInfo`、`LevelError`；
- **一个默认级别**：`LevelError`，即默认只输出错误；
- **一个输出目标**：默认 `os.Stderr`，可通过 `--log-output` 重定向到文件。

#### 分级与输出

```go
// pkg/log/log.go
type Level int

const (
	LevelDebug Level = iota
	LevelInfo
	LevelError
)

var (
	mu     sync.Mutex
	level  = LevelError
	output io.Writer = os.Stderr
)
```

`logf` 先比较级别，再格式化输出；输出格式只有一层前缀：

```go
func logf(l Level, tag, format string, args ...interface{}) {
	mu.Lock()
	defer mu.Unlock()
	if l < level {
		return
	}
	fmt.Fprintf(output, "[%s] %s\n", tag, fmt.Sprintf(format, args...))
}
```

对外只暴露三个函数：

```go
func Debugf(format string, args ...interface{})  // tag = "debug"
func Infof(format string, args ...interface{})   // tag = "info"
func Errorf(format string, args ...interface{})  // tag = "error"
```

`sync.Mutex` 保证多个 goroutine（例如 RPC 服务端与调试会话）同时写日志时不会把一行拆开；级别和输出目标都是全局的，避免在每个组件里重复配置。

#### 命令行开关

日志开关定义在根命令 `cmd/root.go` 的持久 flag 上：

```go
rootCmd.PersistentFlags().Bool("log", false, "enable debug logging")
rootCmd.PersistentFlags().String("log-output", "", "write logs to file instead of stderr")
```

`PersistentPreRun` 在子命令执行前统一应用：

```go
if v, _ := cmd.Flags().GetBool("log"); v {
	log.SetLevel(log.LevelDebug)
}
if f, _ := cmd.Flags().GetString("log-output"); f != "" {
	w, err := os.OpenFile(f, os.O_CREATE|os.O_WRONLY|os.O_APPEND, 0644)
	if err != nil {
		log.Errorf("open log output %s: %v", f, err)
		return
	}
	log.SetOutput(w)
}
```

因此：

```bash
$ godbg --log debug ./main.go          # debug 级别，输出到 stderr
$ godbg --log --log-output /tmp/godbg.log debug ./main.go
```

`--log` 不开时，`Debugf`/`Infof` 都被级别过滤，只有 `Errorf` 会输出；`--log-output` 使用追加模式，多次启动不会覆盖旧日志。

### 使用约定

godbgv2 的后端包（`pkg/target`、`pkg/proc`、`pkg/dwarf`、`pkg/service`）**不允许直接 `fmt.Print`**（见 `docs/ARCH-RULES.md` 铁律 1）。需要记录诊断信息时：

- 只在确实需要排查的位置调用 `log.Debugf`，不要把它当 `printf` 使用；
- 面向用户的输出一律由 `cmd/` 或 `pkg/terminal` 负责；
- 记录错误时优先把上下文写进 `Errorf` 的参数，而不是拼接长字符串。

当前 godbgv2 的日志调用还很少，主要集中在 RPC 装配和根命令配置；这不是缺陷，而是教学版的取舍：先把「分级 + 开关 + 输出目标」这套骨架搭好，后续每加一个子系统，再在关键路径补 `Debugf`。

### 能力边界与扩展方向

godbgv2 当前**没有**以下能力：

- 没有 `Warn` 级别，也没有 `slog` 的结构化字段（key=value）；
- 没有按组件（debugger/rpc/fncall/stack…）拆分的独立 logger 和逐层开关；
- 没有日志轮转、采样、异步落盘。

如果后续需要更细的日志，可以在 `pkg/log` 里增加一个 `Logger` 类型（持有 level/output），再由各子系统注入；但不要为此把 `pkg/log` 变成全局单例的堆叠，否则会重演「日志很多、却不知道来自哪一层」的问题。

### 本节小结

godbgv2 的日志系统只有约 60 行：三级日志、全局级别、可重定向到文件，默认只输出错误。它的价值不在功能多，而在于把「默认安静、需要时能打开、后端不直接打印」这三条约定固定下来。读后续小节时，如果遇到 `log.Debugf`，可以把它当作调试器自身的诊断输出，而不是被调试程序的输出。
