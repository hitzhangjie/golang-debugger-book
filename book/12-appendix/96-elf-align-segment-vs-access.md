## 扩展阅读：ELF 的 align 到底在对齐什么

### 一个容易让人卡住的例子

7.5 节的段头表里有一组看起来自相矛盾的值：

```text
LOAD  off 0x000000  vaddr 0x08048000  filesz 0x000448  memsz 0x000448  R E  align 2**12
LOAD  off 0x000448  vaddr 0x08049448  filesz 0x0000e8  memsz 0x000104  RW   align 2**12
```

数据段的 `align` 是 4KB，可它的虚拟地址 0x08049448 和文件偏移 0x448 都不在 4KB 边界上。于是很容易产生两个疑问：

1. 既然要对齐，为什么数据段不直接放到 0x08049000？
2. 段首没有 4KB 对齐，CPU 读取数据时会不会变慢？

第一个问题的答案在 7.5 节：`p_align` 约束的是“同余”，不是“段首落在边界上”。第二个问题则要把三种不同的“对齐”分开看。

### 三种“对齐”

| | 段/页映射对齐 | 节/符号对齐 | 缓存行对齐 |
|---|---|---|---|
| 典型粒度 | 4KB（页）、2MB（大页） | 1/2/4/8/16/32/64 字节 | 64 字节 |
| 约束 | `p_vaddr ≡ p_offset (mod p_align)` | `sh_addr % sh_addralign == 0`，符号满足 ABI 的对齐要求 | 对象地址尽量落在缓存行边界 |
| 谁保证 | 链接器 + 内核加载器 | 编译器 + 链接器 | 编译器/程序员 |
| 目的 | 文件页能直接映射成内存页（零拷贝） | ABI 正确、单次访问不跨缓存行 | 减少缓存行拆分和伪共享 |
| 谁在意 | `mmap`、页表 | CPU 的 load/store | CPU cache |

平时说“对齐能加速读取”，说的是后两种。`p_align` 属于第一种，它首先是**映射正确性**问题：不满足同余，`mmap` 就没法直接把文件页映射到目标虚拟页。

### `p_align` 的准确含义

ELF gABI 对可装载段的原文是：

> Loadable process segments must have congruent values for `p_vaddr` and `p_offset`, modulo the page size. ... `p_vaddr` should equal `p_offset`, modulo `p_align`.

也就是说，`p_vaddr` 和 `p_offset` 对 `p_align` 取模必须相等。以 7.5 节的数据段为例：

```text
0x08049448 mod 0x1000 = 0x448
0x00000448 mod 0x1000 = 0x448
```

余数相同，约束满足。真正落在 4KB 边界上的是**页基址**：

```text
内存页基址 = 0x08049448 & ~0xfff = 0x08049000
文件页基址 = 0x00000448 & ~0xfff = 0x00000000
```

加载器实际做的是（Linux `elf_map()` 的简化，4KB 页）：

```c
off  = p_offset - (p_vaddr & 0xfff);   // 0x448 - 0x448 = 0x0
addr = p_vaddr & ~0xfff;               // 0x08049000
size = p_filesz + (p_vaddr & 0xfff);   // 0xe8 + 0x448
mmap(addr, size, prot, MAP_FIXED | MAP_PRIVATE, fd, off);
```

`mmap` 要求文件偏移 `off` 页对齐。只有 `p_vaddr` 和 `p_offset` 同余，`p_offset - (p_vaddr & 0xfff)` 才落在页边界上；映射建立后，文件偏移 0x448 的字节正好落在 `0x08049000 + 0x448 = 0x08049448`。

如果不同余，`off` 不是页对齐，`mmap` 会返回 `EINVAL`。想在内存里得到同样的段内容，就只能先把文件读进临时缓冲区，再拷贝到目标地址——exec 更慢，还多一份内存。所以同余不是“为了好看”，而是零拷贝映射的前提。

`p_align` 不一定等于页大小，也可能更大（本机 GNU ld 默认 `max-page-size=2MB`）。规则仍然是 `p_vaddr ≡ p_offset (mod p_align)`；对页大小同余是 `mmap` 能工作的最低要求。

### 段首不在页边界，为什么访问不会变慢

关键点：**CPU 访问的是具体的变量和指令，不是段的起始地址；变量和指令的对齐由编译器和链接器逐层保证，和段首在页内的位置无关。**

分三层看：

1. **编译器**按 ABI 给每个对象对齐。比如 x86-64 上 `int64` 要求 8 字节对齐，编译器会把全局变量、结构体成员放到满足类型对齐要求的偏移上（C 里的 `_Alignof` 是其中一种表述），不够就插 padding。
2. **链接器**合并输入节、分配输出节地址时，保证 `sh_addr % sh_addralign == 0`；节与节之间不够对齐就插 padding。
3. 链接器给整个段选一对 `(p_offset, p_vaddr)`，并要求 `p_vaddr ≡ p_offset (mod p_align)`，也就是平移量 `C = p_vaddr - p_offset` 是 `p_align` 的整数倍。段内有文件内容的任意字节都满足 `vaddr = file_offset + C`，所以**文件侧和内存侧的低位对齐关系完全一致**。

第三点是“段内保证”的核心。换个说法：段首在页内偏移 0xe00，不代表段里的变量都偏了 0xe00；整个段在文件和内存里平移了同一个 `C`，节和符号的相对布局没变。只要 `C` 是页大小的整数倍，`C` 的低 12 位就是 0，所有不超过页大小的对齐（4/8/16/32/64 字节）在两侧同时成立。反过来，如果 `C` 不是页大小的整数倍，同余就不成立，`mmap` 的 `off` 也不会页对齐。所以同余约束和“段内对齐在文件/内存两侧保持一致”是同一件事的两面。

用本机编一个 C 程序看得更清楚（GNU ld 默认 `max-page-size=2MB`）：

```c
#include <stdio.h>
long i64;
long arr[4];
const char *msg = "hello";

int main(void) {
    printf("%ld %ld %s\n", i64, arr[0], msg);
    return 0;
}
```

```bash
$ gcc -no-pie -O0 -o a a.c
$ readelf -lW a
# 只看两个 LOAD 段，省略其他 program header
  Type   Offset   VirtAddr           PhysAddr           FileSiz  MemSiz   Flg Align
  LOAD   0x000000 0x0000000000400000 0x0000000000400000 0x0007a0 0x0007a0 R E 0x200000
  LOAD   0x000e00 0x0000000000600e00 0x0000000000600e00 0x000230 0x0002a0 RW  0x200000
$ readelf -SW a | grep -E '\.(init_array|got|data|bss)'
# 只看几个关键节，省略部分列和无关节
  [18] .init_array INIT_ARRAY 0000000000600e00 000e00 000008 08 WA  0   0  8
  [21] .got        PROGBITS   0000000000600fe0 000fe0 000020 08 WA  0   0  8
  [23] .data       PROGBITS   0000000000601020 001020 000010 00 WA  0   0  8
  [24] .bss        NOBITS     0000000000601040 001030 000060 00 WA  0   0 32
```

数据段的 `p_offset` 是 0xe00，`p_vaddr` 是 0x600e00，都不是 4KB 对齐，`align` 甚至还写着 2MB；但 `.init_array`、`.got`、`.data` 都在 8 字节边界上，`.bss` 在 32 字节边界上。原因就是：

```text
C = p_vaddr - p_offset = 0x600e00 - 0x000e00 = 0x600000 = 3 × 0x200000
```

`C` 的 2MB 以下低位全是 0，节在内存里的对齐原封不动地映射到文件里。加载器只把这一个段整体平移，完全不用逐字节调整。

> `.bss` 是 `NOBITS`，文件里没有对应内容，`Off` 列只是占位，不能拿它来验证 `vaddr = file_offset + C`。看 `Address` 和 `Al` 两列即可。

### “段内保证”到底保证了什么

把上面的三层合起来：

- 编译器保证**对象在节内的偏移**满足对象的对齐；
- 链接器保证**节在段内的偏移**满足节的 `sh_addralign`；
- 链接器保证**段在文件/内存之间的平移量 `C`** 是 `p_align` 的整数倍。

三段拼起来，对象最终的绝对地址（`p_vaddr + 节偏移 + 对象偏移`）满足 ABI 对齐；同时文件偏移和虚拟地址的低位一致，`mmap` 可以直接建立映射。这三层都在链接时完成；运行时加载器只按段建立页映射，不会再调整节或符号的地址。

所以“段内对齐”不是“段首必须对齐”，而是“段内每个节、每个符号按自己的要求对齐，段的页内偏移只是整体平移”。段首的 0x448/0xe00 是平移量的一部分，不是错位。

### 为什么链接器不把文件偏移补齐到 4KB

因为没必要，而且有代价：

- 同余已经满足 `mmap`；文件偏移可以紧接上一段（7.5 节的例子就是代码段 filesz 结束在 0x448，数据段从 0x448 开始），省掉填充字节。
- 若把数据段的文件偏移补到 0x1000，虚拟地址也得取 0x08049000（否则不同余）；文件大了 0xbb8 字节，运行时没有任何收益。
- 数据段之所以从页 0x08049000 而不是紧接代码段 0x08048448 开始，是因为代码页 R E、数据页 RW，页权限按页生效，两者不能共用一个内存页。页基址定了，段首的页内偏移就必须和文件偏移一致，于是是 0x448，而不是 0。

链接器真正的目标是把文件排紧、把内存按权限分页。这两个目标用“同余 + 页基址对齐”就能同时满足。

### 一个容易忽略的细节：同一个文件页可能映射两次

按页映射意味着，数据段映射的页会把文件里它前面的字节也带进来。7.5 节的例子中，数据段从文件页 0 映射到内存页 0x08049000，而文件页 0 的前 0x448 字节正是代码段的内容。于是同一文件页在 0x08048000（R E）和 0x08049000（RW）各有一份映射。

这不会让程序把代码当数据用：数据段的 `memsz` 只覆盖 0x08049448 开始的范围，页内多出来的那部分不在段的地址范围内，程序不会访问。`MAP_PRIVATE` 下写入还会触发写时复制，两份映射互不影响。现代链接器用 `-z separate-code`、`max-page-size` 把不同权限的段放到不同的内存页，主要是为了满足页权限和 W^X，而不是因为同余本身有问题。

### 小结

- `p_align` 的 4KB 是页大小，约束的是 `p_vaddr ≡ p_offset (mod p_align)`；段首本身不必落在 4KB 边界。
- 真正落在页边界上的是 `mmap` 的页基址：内存侧 `p_vaddr & ~0xfff`，文件侧 `p_offset & ~0xfff`。
- 段首在页内的偏移不影响 CPU 访问；变量/指令的对齐由编译器（对象偏移）、链接器（节地址、段平移量 `C`）共同保证。
- 段平移量 `C = p_vaddr - p_offset` 是 `p_align` 的整数倍，所以文件侧和内存侧的低位对齐关系完全一致。
- 把文件偏移补到 4KB 边界没有运行收益；同余加页基址对齐已经足够。
