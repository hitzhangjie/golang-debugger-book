## AI助力软件逆向

### 使用门槛

指令级调试长期以来不好做，主要卡在两个地方。

一个是指令集。机器码反汇编之后，看到的是 `mov`、`lea`、`call`，再加上寄存器和立即数。这些助记符如果对不上指令的含义，程序在做什么就读不出来。Go 里一句 `fmt.Println`，落到 x86-64 上还要再看调用约定、栈检查和 `morestack`。第 6 章用 radare2 的 `pdf` 打出的 `main.main`，就是这种阅读量。

另一个是工具。radare2、Ghidra、IDA Pro、Hopper、Binary Ninja 早就能做反汇编和反编译，可是分析流程、命令，以及呈现出来的数据组织，各不一样。很多人把工具装上了，却不知道从哪里定位函数，怎么顺着调用关系往下看，又怎么改掉其中几条指令。

所以，会写 Go、会用 dlv，并不就会读一段没有符号的汇编，也不一定能够照着反编译结果去改一个函数。二进制分析要另学指令集，也要另学这些工具。

### 反汇编与反编译

这两件事经常被放在一起说，做的时候要分开。

反汇编（disassembly）是把机器指令还原成汇编助记符。第 6 章的 `disass` 就是在做这件事：从 ELF 的代码段取出字节，用 `golang.org/x/arch/x86/x86asm` 一条条解码。radare2 的 `pdf` 也是反汇编，只是它还会标出跳转，以及栈上的变量槽位。

反编译（decompilation）再往上走一步，把指令提升成接近高级语言的伪代码。Ghidra 的反编译器、Hex-Rays 做的就是这个。伪代码读起来省事一些，但它是分析器推断出来的，和编译器当初的源码不是同一份结果。类型恢复错了，或者函数被内联、控制流被优化打乱，伪代码就会和真实指令对不上。

真要改程序的行为，还是得回到指令上：看清要改哪几个字节，patch 完再验证。反编译用来理解逻辑，反汇编和调试用来定位和修改。

### 把能力包进 MCP

模型并没有换掉这些引擎。Capstone、Ghidra、radare2 该做的解码和分析，仍然由它们完成。变的是谁来操作它们。

模型上下文协议（Model Context Protocol，MCP）把打开二进制、反汇编、反编译、查交叉引用、读字符串这些动作，定义成编程代理可以调用的工具。代理在本机把工具跑起来，读回结果，再决定下一步问什么。

这和[《AI助力软件调试》](./9-ai-assisted-software-debugging.md)是同一类做法，分析的对象不一样。那一节里，代理通过调试器的输入输出去单步、看变量，面对的是带源码的程序。这一节里，代理通过逆向工具去读指令和伪代码，面对的常常是没有源码，或者源码和二进制对不上的程序。

围绕单个引擎，已经有一批专门的 MCP 服务。GhidraMCP 把正在运行的 Ghidra 暴露给代理；Hex-Rays 提供了官方的 IDA MCP；radare2 的 r2mcp 可以从命令行、插件或者远程会话里调用 r2，并且支持只读模式和沙箱限制。它们各自对着一个引擎。

### REA

[REA](https://github.com/morluto/rea)（Reverse Engineer Anything）把多种分析收进同一个入口。它是一个开源的 MCP 服务，采用 MIT 许可证，源码在 [morluto/rea](https://github.com/morluto/rea)，也可以通过 npm 包 `rea-agents` 安装，文档在 [rea.tools](https://rea.tools/)。

REA 自己不重新实现反汇编器和反编译器。它调用本机已经装好的引擎，再把结果整理成带证据的发现。看原生二进制时，可以用 Ghidra、Hopper 或 IDA 取出伪代码、汇编、符号、调用和交叉引用；只做离线查看时，也可以用调用方自己提供的 GNU objdump 或 Rizin。Ghidra、Rizin 是开源的。IDA、Hopper、JEB 是商业软件，授权要单独准备，REA 不附带这些许可证。

除了原生指令，它还能看一些不需要完整反编译器的目标：Go 二进制里嵌着的编译器版本、模块和构建参数，Rust 二进制里的 crate 信息，JavaScript / Electron 的模块和 IPC，.NET 程序集，Android APK，以及网站和抓包。这些结果不都是机器码到汇编的转换，但都在回答同一个问题：这个程序到底做了什么。

分析默认在本地进行。`rea mcp` 通过标准输入输出和 Cursor、Claude Code 这类客户端通信，不另外监听网络端口。代理拿到的是工具返回的结果；这些结果会不会离开本机，还要看所用模型服务自己的数据策略。

本机有 Node.js 和 npm 时，可以用下面的命令把 REA 注册到代理里。它会先列出要改的配置，确认之后才写入，并带上对应的工作流说明。写完需要重启代理。不通过对话也可以，命令行里能直接做同一套分析。

```bash
npx rea-agents setup
```

### 一次分析是怎么进行的

以前要自己在 radare2 里选命令、读输出。交给代理之后，一轮分析大致是这样：

1. 用自然语言说明要看哪个程序、想弄清什么问题，并要求给出证据。
2. 代理通过 MCP 调用 REA。REA 按目标类型选择引擎，做反汇编、反编译，并查询引用关系。
3. 工具返回伪代码、汇编、调用关系，也返回它还不能确定的部分。每条结论旁边都有证据，以及这条结论的局限。
4. 代理根据这些材料解释程序的行为。需要的话，再继续看下一个函数，或者按要求写出一份对照实现，并用测试去对。

REA 网站上的 Windows Calculator 案例把这个过程摊开了。问题是：为什么 `200 + 10%` 得到 220，而不是 210。REA 从已经安装的 Calculator 程序里取出处理百分号的指令，其中能看到对 `0x5b`、`0x5c` 的比较，以及常量 `0x64`（十进制 100）。对照微软公开源码里的按钮编号，`0x5c` 是乘法，`0x5b` 是除法。走加法时，百分号取的是前一个操作数的百分之几：10% of 200 = 20，再算 200 + 20。走乘法时，百分号被收成 0.1。指令给出比较、常量和跳转，反编译结果给出控制流，代理负责把两边对上，并说明依据的是哪一段指令。

在 radare2 里执行 `s`、`af`、`pdf` 再自己读结果，看到的是同一类信息。差别在于，选哪条命令、留哪些结果、这段跳转在说什么，交给了代理。人要做的是核对证据，并决定下一个问题。

官方还有两个更完整的重建案例，可以看出这种做法能走到哪一步。[DX-Ball](https://rea.tools/showcase/dx-ball/) 从声音定位跟到位置换算，把不完整的伪代码整理成 C，并用原始 x86 指令的测试用例核对。[TH04](https://rea.tools/showcase/th04/) 从 PC-98 游戏的 16 位指令里恢复弹幕的角度计算。两个案例都要求写出来的代码对得上原始指令，不能停在一段只是好读的伪代码上。

### 和前面章节的关系

第 6 章已经把反汇编从字节走到助记符的路径讲过了：怎么根据进程找到可执行文件，怎么解析 ELF，变长指令怎么解码，以及断点把指令改成 `0xCC` 之后，为什么要先还原再反汇编。多了一个 MCP，这些步骤仍然要搞清楚。

代理会出错，反编译引擎也会出错。伪代码里的类型一旦恢复错了，模型就可能顺着这个错误，把整个函数解释得前后一致。这时候要回到指令，看跳转目标、立即数和真实的调用地址。第 6 章的 `disass`，以及后面符号级调试用到的 DWARF，就是用来做这个核对的。

程序带着源码和调试信息时，优先用符号级调试，也可以用上一节讲的自动化调试。没有源码、符号被剥离，或者要看的就是编译器最终发出的指令时，再用这里的方法。两条路可以接起来：先用反编译把函数范围缩小，再在调试器里对那个地址下断点。

### 能解决什么，不能解决什么

MCP 减轻的是工具不会用这一层。不必先记住 radare2 的全部命令，也可以让代理去调用 Ghidra 或 r2，把一个函数的汇编和伪代码取回来，再说明它在做什么。调试和反编译原来散在不同软件里，现在被收成同一套可以调用的接口。REA 这层封装是开源的，可以在此基础上继续改。

指令本身的难度还在，结论也仍然要靠证据来核对。

- 模型可能给出一段说得通、但没有指令依据的解释。REA 要求结果带上证据和局限，所以要看它引用了哪几条指令，不能只看最后的总结。
- 反编译的质量取决于底层引擎。优化过的代码、手写汇编、加壳和混淆，仍然会让反编译失败，或者让结果和真实指令对不上。
- REA、Ghidra、radare2 是开源的。IDA、Hopper、JEB 仍然需要各自的商业授权。
- 被分析的程序应当是有权检查的。REA 自己把用途限定在研究、教学、互操作和软件保存，以及由软件所有者或得到授权的人来做分析。

把第 6 章的反汇编学扎实，才判断得了代理拿回来的汇编能不能信。MCP 和 REA 改变的是谁去调用这些工具，指令的含义并没有变。

### 本节小结

本节主要讨论了 AI 接入反汇编和反编译之后，分析工作是怎么进行的。核心内容包括：门槛来自指令集和工具使用；反汇编给出助记符，反编译给出伪代码，修改二进制仍然要回到指令；REA 这类开源 MCP 服务调用 Ghidra、IDA、radare2 等现有引擎，并要求结果带上证据。本节接上第 6 章的指令级调试，也接上上一节的自动化调试，帮助读者判断代理给出的汇编解释有没有指令依据。
